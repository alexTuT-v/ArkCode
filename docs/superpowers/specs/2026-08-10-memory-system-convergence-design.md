# ArkCode 自动记忆系统向 MewCode 收敛设计

## 1. 背景

ArkCode 当前已经具备长期记忆的基本能力：模型可以输出 `create`、`update`、`delete` JSON action，`Manager` 将 action 按项目级和用户级分发给 `Store`，`Store` 负责维护独立 Markdown 记忆文件并重建 `MEMORY.md`。

当前主要不足不是文件格式，而是记忆生命周期不完整：自动提取触发较稀疏、后台任务缺少收尾保证、召回只注入摘要索引、语义重复主要依赖提取提示词，也没有周期性整理机制。

本设计借鉴 MewCode 的三层记忆链路：每轮自动提取、按需召回全文、周期整理去重。同时保留 ArkCode 更明确的 JSON action、文件名校验和统一 Store 写入边界。

## 2. 目标

- 每个正常完成的对话轮次都能异步提取长期记忆。
- 自动提取不会重复消费系统提示、工具内容或已经注入的记忆。
- 每轮可根据当前问题召回最多 5 条相关记忆全文。
- 周期性合并近义重复、处理冲突和删除过期记忆。
- 所有记忆修改统一使用 JSON action 和 `Store`，不允许模型任意操作文件。
- 记忆后台任务不会阻塞正常对话，并在程序退出时获得有限的收尾时间。
- 不向 `conversation.jsonl` 追加记忆 action 或记忆文件快照。

## 3. 非目标

- 不兼容旧版自动记忆输出格式。
- 不引入向量数据库、Embedding、指纹或相似度算法。
- 不实现跨目录事务和操作回滚日志。
- 不持久化待提取的 turn batch。
- 第一版周期整理不搜索历史 conversation。
- 不开放 Bash、任意路径读写或通用 Agent 给记忆维护模型。

## 4. 总体链路

```text
用户提交消息
  ├─ 读取精简 MEMORY.md 索引
  ├─ 辅助模型选择最多 5 条候选记忆
  ├─ Store 安全读取候选全文
  └─ 主模型使用索引和召回全文回答

正常完成一个 turn
  └─ 后台提取该 turn 的稳定信息
       └─ JSON actions → 校验 → Store 执行 → 重建 MEMORY.md

满足 24 小时且新增 5 个 session
  └─ 后台整理现有记忆
       └─ JSON actions → 校验 → Store 执行 → 重建 MEMORY.md
```

系统只保留三个职责明确的入口：

- `Manager.extract(...)`：增量提取。
- `Recall.select(...)`：相关记忆召回。
- `Consolidator.run(...)`：周期整理和去重。

文件枚举、读取、校验、写入和索引重建继续由 `Store` 负责。

## 5. 统一记忆清单

`Store` 提供结构化的只读清单，供提取、召回和整理复用。每项至少包含：

```text
scope       user | project
type        记忆类型
filename    受 Store 规则约束的相对文件名
title       标题
preview     正文的精简单行摘要
updated_at  最近更新时间
```

外部组件使用 `user:<filename>` 或 `project:<filename>` 作为唯一候选键。模型不会看到或返回绝对路径，文件读取只能通过对应 scope 的 `Store` 完成。

本设计不增加独立 Catalog、数据库或缓存层。

## 6. JSON action 协议

记忆维护模型只返回一个 JSON 数组：

```json
[
  {
    "action": "create",
    "level": "user",
    "type": "user_preference",
    "title": "回答语言偏好",
    "slug": "response_language",
    "content": "用户偏好使用中文回答。",
    "filename": ""
  }
]
```

支持三种操作：

- `create`：使用 `type + slug` 生成文件名并写入完整记忆。
- `update`：按 `level + filename` 覆盖更新完整记忆。
- `delete`：按 `level + filename` 删除记忆。

JSON action 是模型与记忆存储层之间的瞬时操作协议。执行完成后直接丢弃，不写入 `conversation.jsonl`，也不追加到记忆 Markdown 文件。

### 6.1 解析和校验

解析器只做有限容错：

1. 拼接模型的完整文本输出。
2. 去除可选的单层 `json` Markdown 代码围栏。
3. 提取第一个完整 JSON 数组。
4. 使用 `json.loads` 解析。
5. 在执行任何文件操作之前，校验数组中全部 action 和字段。

以下情况整批拒绝：

- 顶层不是数组。
- 数组元素不是对象。
- `action`、`level` 或 `type` 不在允许集合中。
- `create` 缺少合法的 `slug`、`title` 或 `content`。
- `update`、`delete` 缺少合法 `filename`。
- 返回的 scope、type 与目标文件不一致。
- 输出包含无法明确提取的多个 JSON 数组。

空数组 `[]` 是合法结果，表示该批次没有值得保存的内容。

### 6.2 执行规则

- action 按模型返回顺序执行。
- `create` 的目标文件已经存在时，规范化为 `update`，保留原 `created` 时间。
- `update` 使用新内容替换旧内容；不会在旧正文后追加。
- `delete` 对不存在的合法文件视为幂等成功。
- 所有 action 执行结束后，项目级和用户级 `MEMORY.md` 都按实际文件重新生成。
- 不实现跨 Store 回滚；若发生 I/O 错误，确保索引按已经落盘的真实文件重建，并记录失败供下次重新提取或整理。

## 7. 自动提取

### 7.1 触发条件

每个自然完成的 turn 都触发一次后台提取，不再使用“每 5 轮”或关键词命中作为主要条件。

以下结束状态不触发：

- 用户取消。
- Provider 或流式响应错误。
- assistant 没有可见文本。
- 达到最大迭代次数等异常终止。

### 7.2 提取输入

提取批次只包含本轮新增的语义消息：

- 用户真实输入文本。
- assistant 最终对用户可见的文本。

以下内容必须排除：

- system prompt 和 system reminder。
- thinking、signature 和内部推理字段。
- 工具参数、工具调用结果和工具错误详情。
- 本轮注入的 `MEMORY.md` 或召回全文。
- compact 摘要中已经消费过的历史信息。

提取模型同时接收统一记忆清单，以便优先更新已有条目，而不是创建近似副本。

### 7.3 并发和确认

- 同一 `Manager` 最多运行一个提取请求。
- 提取进行中产生的新 turn 放入内存 pending 集合。
- 当前提取结束后，将 pending turn 合并成下一批继续处理。
- 只有得到合法 `[]` 或 actions 成功执行后，该批次才算已消费。
- 首次失败时将当前批次放回 pending，在下一次自然触发或退出收尾时重试一次。
- 同一批次连续失败两次后记录并丢弃，避免永久阻塞后续 turn。
- 不将 pending 批次写入磁盘；进程崩溃时允许丢失尚未完成的最后一批。

应用正常退出时等待当前或 pending 提取最多 3 秒，超时后取消等待，不阻塞退出。

## 8. 选择性召回

每个用户 turn 在主模型第一次请求前执行一次召回：

1. 读取项目级和用户级统一记忆清单。
2. 将当前用户问题和清单交给辅助模型。
3. 辅助模型返回最多 5 个候选键。
4. 校验键确实存在于本次清单，并去除重复项。
5. 通过对应 `Store` 读取完整 Markdown。
6. 将召回内容作为只读 reminder 注入当前 turn，且只注入一次。

召回模型只能选择现有候选键，不能构造路径。完整召回内容按模型返回顺序注入，总量上限为 25 KiB；超过上限时在 UTF-8 字符边界截断最后一条。

召回最多等待 5 秒。解析错误、Provider 错误、超时或没有候选时，继续使用现有精简 `MEMORY.md` 索引，不影响主对话。

第一版不实现向量检索、相关度分数、召回缓存或跨 turn 已读状态。

## 9. 周期整理和去重

周期整理仅在以下两个条件同时满足时触发：

- 距离上次成功整理至少 24 小时。
- 上次成功整理后新增至少 5 个 session。

运行状态保存在项目记忆目录的 `.consolidation-state.json`，只记录上次成功时间和当时可读取的 session 文件总数。当前 session 文件总数比基线至少增加 5 时，满足 session 条件。进程内使用单任务保护，同一时间最多运行一个整理任务，不增加跨进程复杂锁。

整理模型读取统一记忆清单和现有记忆正文，负责：

- 合并表达不同但语义相同的条目。
- 将同一主题的增量信息更新到已有条目。
- 删除已经被明确推翻或失效的内容。
- 在不能确定冲突真伪时保留信息，不擅自删除。

整理模型使用与自动提取相同的 JSON action 协议和 Store 执行路径。只有 action 校验、执行及索引重建全部完成，才更新整理成功时间和 session 基线。

第一版不读取历史 transcript，也不通过通用 Agent 或文件工具自行修改记忆目录。

## 10. 错误处理

- 提取、召回和整理失败均记录结构化日志，但不终止主对话。
- 非法 JSON 或非法 action 不执行任何业务文件操作。
- 召回失败立即降级为精简索引。
- 提取首次失败保留内存 pending 批次；连续失败两次后丢弃该批次。
- 整理失败不更新成功时间和 session 基线，之后仍可重新触发。
- Store I/O 失败不做复杂事务回滚，但必须按当前真实文件状态重建索引。

## 11. 测试范围

### 11.1 JSON action 与 Store

- 解析纯 JSON、带 `json` 围栏的 JSON 和 `[]`。
- 非数组、多个数组、非法字段和非法文件名整批拒绝。
- 同名 `create` 转换为 `update` 并保留 `created`。
- `update` 覆盖正文而不是追加正文。
- `delete` 幂等。
- action 不写入 conversation JSONL。
- 执行后 `MEMORY.md` 与实际文件一致。

### 11.2 自动提取

- 每个正常 turn 都触发。
- 取消、错误、空响应和异常终止不触发。
- 工具消息、thinking、reminder 和旧记忆不会进入提取输入。
- 连续 turn 在单活跃任务和 pending 模式下不重复、不漏掉已完成批次。
- 合法 `[]` 会确认消费；非法输出不会确认消费。
- 同一批次最多重试一次，连续失败不会阻塞后续批次。
- 退出等待不超过 3 秒。

### 11.3 召回

- 最多接受 5 个存在于清单中的唯一候选键。
- 模型不能越过 Store 读取任意路径。
- 全文总量不超过 25 KiB。
- 每个 turn 最多注入一次。
- 超时、非法响应和 Provider 错误会回退到精简索引。

### 11.4 周期整理

- 24 小时与新增 5 个 session 必须同时满足。
- 同一时间不会并行运行两个整理任务。
- 失败不会推进整理基线。
- 成功合并重复记忆后会删除旧文件并重建索引。

## 12. 验收标准

- 连续完成多个自然 turn 时，每轮语义内容恰好进入一次自动提取链路。
- 同一稳定事实不会因为同名 `create` 产生追加内容或重复文件。
- 用户提问命中已有记忆时，主模型可获得最多 5 条相关记忆全文。
- 达到周期条件后，系统能够使用统一 JSON action 合并重复条目。
- 任何记忆模型输出都不能绕过 Store 写入任意路径。
- `conversation.jsonl` 不保存记忆 action、记忆正文快照或周期整理过程。
- 自动记忆功能失败时，普通对话仍可继续。

## 13. 明确取舍

本方案采用 MewCode 的触发时机和三层生命周期，但不照搬文本块输出、直接路径写入和通用 Agent 整理方式。ArkCode 继续使用 JSON action，以较小的解析成本换取明确的操作语义、路径安全和可测试性。

第一版优先建立稳定闭环，不通过向量检索、复杂事务、持久任务队列或 transcript 搜索追求过早的完备性。
